System Walkthrough

Kokiri

A personal AI operations system: one shared context layer, model-agnostic intelligence, and agents that can actually take action — not just chat.

A note on this page: this is a guided tour of the system's architecture and design decisions, written for review rather than daily use. All examples below (business names, numbers, keys, conversations) are illustrative placeholders — the real system runs on a single private Supabase project with a single authenticated user, and no actual account data appears anywhere on this page.

01

Why This Exists

Most people who use AI tools end up with a scattered set of them: one chat window for writing, another app for scheduling, a separate dashboard for tracking a business, disconnected browser tabs for each service they use. Every tool starts from zero — no memory of yesterday's conversation, no awareness of what any other tool knows.

Kokiri started from a different premise: what if there were one place a person's operational life lived — their tasks, their business data, their communications — and a layer of AI "agents" that could read and act on all of it, regardless of which underlying model happened to be answering at the time?

The guiding idea is closer to chief-of-staff than chatbot. A chief of staff doesn't need to be re-briefed every conversation. They remember context, they know which specialist to loop in, and — critically — they can actually go do the thing, not just describe how you might do it yourself.

A secondary, equally deliberate goal: stay free until it has to be free-er. The system is built to run entirely on free-tier infrastructure and free language models by default, only reaching for paid intelligence when the task genuinely demands it. That constraint shaped almost every architectural decision below.

02

System Architecture

Kokiri is a static frontend (plain HTML/CSS/JavaScript, no build step, no framework) hosted on free static hosting, talking directly to a managed backend-as-a-service platform that provides the database, authentication, serverless functions, and file storage.

┌─────────────────────────────────────────────────────────┐ │ Static Frontend (HTML / JS, no build step, free hosting) │ │ dashboard · sheets · dashboards · repository · portals │ └───────────────────────────┬─────────────────────────────┘ │ direct client calls ▼ ┌─────────────────────────────────────────────────────────┐ │ Backend Platform (managed Postgres + Auth + Storage) │ │ │ │ Postgres rows-as-data model, row-level security │ │ Auth single authenticated owner account │ │ Vault encrypted secret storage, tiered access │ │ Storage private file bucket (documents/media) │ │ Edge Functions serverless request handlers (see below) │ │ Scheduler cron-style jobs for recurring work │ └───────────────────────────┬─────────────────────────────┘ │ outbound HTTP ▼ ┌─────────────────────────────────────────────────────────┐ │ External Services │ │ LLM providers · messaging platforms · third-party APIs │ │ · MCP-compatible tool servers │ └─────────────────────────────────────────────────────────┘

Every "feature" in Kokiri — a dashboard, a chat surface, a webhook — is really just a thin client over this same backend. There is no separate application server; the serverless functions are the application server, and they're stateless by design: every request re-fetches whatever context it needs from Postgres, so there's nothing to keep in sync and nothing that can silently drift out of date.

Data model philosophy

Rather than hard-coding a schema for every kind of tracked thing (a CRM table, an ads table, a content calendar table...), the core of the system uses one generic three-table pattern: a sheet defines a named collection, columns define its schema, and rows hold flexible key-value data. Every dashboard in the system — CRM, ad performance, content calendar, task board — is the same generic spreadsheet engine pointed at a different sheet. New tracked categories don't require new code, just a new sheet definition.

03

The Agent Model

An "agent" in Kokiri is deliberately lightweight: a row in a table with a name, a purpose, an icon, a status, and a model preference. Creating an agent doesn't generate any new code — it just adds data that a single shared function reads.

Illustrative example An agent named "Scout" with the purpose "monitor inbound leads and draft first-touch replies" is, structurally, nothing more than one row: { name: "Scout", purpose: "...", status: "active", model_pref: "auto" }. Everything Scout is able to do comes from the shared systems described in the rest of this page, not from anything unique written for Scout.

Every agent conversation is assembled fresh, on every message, by one prompt-building function. That function pulls in:

  • The agent's own name and stated purpose
  • A global context block the system owner maintains once, centrally (see Context Scoping — this can be included or withheld per agent)
  • The list of other agents that exist, so agents can hand off or reference each other
  • Whichever data sheets and external tools that specific agent has been granted access to

This means updating one piece of shared context — say, a change in operating hours or a new standing instruction — propagates to every agent's next reply immediately, without touching any agent individually.

04

Model-Agnostic Intelligence

The assembled prompt is deliberately decoupled from any specific language model. A request cascades through tiers until one succeeds:

request │ ▼ Tier 1 — Premium / free-router models (cloud, tried first) │ on timeout / rate-limit / failure ▼ Tier 2 — Free community-hosted models (cloud, no cost) │ on timeout / failure ▼ Tier 3 — Locally-run open models (self-hosted, no cost, no external dependency) │ ▼ first successful reply wins

The practical effect is that the system essentially never hard-fails on "the AI is unavailable" — it degrades gracefully through progressively cheaper (and eventually free, local) intelligence rather than stopping. The prompt itself, the tools available, and the actions the model can take are identical regardless of which tier answered; only response quality varies.

05

The Action Protocol

The single biggest design decision in the system: rather than relying on a specific provider's native "function calling" feature (which varies or doesn't exist across free models), Kokiri defines its own minimal, provider-agnostic action grammar. Any model — expensive or free, hosted or local — can trigger a real action by ending its reply with one small JSON block.

Illustrative model output Got it — I've logged that as a new task for Scout.
[ACTION]{"type":"create_task","agent":"Scout","title":"Follow up with new lead","description":"..."}[/ACTION]

The frontend/backend code parses that block out of the reply, executes the corresponding real operation (inserting a task, querying live data, calling an external tool), strips the raw JSON from what the user actually sees, and — for read operations — feeds the result back to the model in a follow-up turn so it can answer using real data instead of guessing.

Because this protocol lives entirely in the prompt and a small amount of parsing code, it works identically whether the reply came from a frontier model or a free, locally-run one — which is what makes the free-tier fallback cascade viable without losing capability.

06

Tool Integration (MCP & REST)

Two complementary integration layers let agents reach outside the system:

🔌

MCP Client

A from-scratch client implementing the Model Context Protocol: JSON-RPC session negotiation, remote tool discovery, and OAuth 2.0 with dynamic client registration and PKCE for servers that require it — the same open protocol used by several mainstream AI assistants, so any compliant third-party tool server can be connected without custom integration code.

🌐

Generic REST Connector

For the far larger number of services that don't speak MCP: a template-substitution connector where a defined "action" (endpoint, method, auth type, body shape) becomes callable by name, with credentials always resolved server-side and never exposed to the model or the browser.

From the model's perspective, both are exposed identically through the same action grammar described above — it doesn't need to know or care whether a given capability is backed by MCP or a plain REST call.

07

Context Scoping

By default, every agent shares the same global context and the same set of connected tools — deliberately, since the whole point is a unified operating picture. But some agents should legitimately see less. An agent handling one narrow function shouldn't necessarily have standing access to every data sheet or every connected service.

Each agent can be switched from Global access to Custom, at which point an explicit checklist controls exactly what that agent's prompt is allowed to reference: which data sheets, which tool servers, and whether the shared global context text is included at all.

LayerWhat it does
Prompt-levelA scoped agent's system prompt simply omits anything outside its granted scope — it has no way to know an out-of-scope sheet or tool exists.
Execution-levelIndependent of what the prompt says, the function that actually executes a requested action re-checks the agent's granted scope and rejects anything outside it — a defense-in-depth measure against a model attempting an out-of-scope call regardless of prompt wording.

This turns "one shared brain" into "one shared brain, selectively partitioned per role" without needing separate credentials, separate databases, or separate deployments per agent.

08

Multi-Channel Access

The same intelligence, memory, and action capability available in the web dashboard is also reachable from ordinary messaging apps, so the system doesn't require sitting at a desk to use.

✈️ Telegram 💬 Slack 📱 WhatsApp

Each platform's webhook verifies the inbound request is authentic (a shared-secret header, or an HMAC signature over the raw request body, depending on the platform's own security model), then hands the message to the same underlying conversation engine the dashboard uses. One conversation thread is kept per platform-and-contact pair, with recent history fed back in on every message — the same threading and memory model as the in-app chat, just reachable from a phone's default messaging apps instead of a browser tab.

Because webhook handlers must typically acknowledge receipt within a few seconds (a platform-imposed constraint, not a Kokiri one), the actual language-model round-trip runs in the background after an immediate acknowledgment is sent — so a slower model tier never causes the platform to treat the message as failed.

09

Security Model

Secrets (API keys, tokens, signing secrets) are handled with a deliberate three-tier model rather than one blanket policy, because "how a secret is written" and "how it's read back" need different guarantees:

TierRead accessUsed for
Server-only vaultBackend service role only — never the browser, never the modelPlatform signing secrets, tokens that must never be exposed client-side
Write-only vaultThe owner's browser can write a new secret, but nothing can ever read the raw value back out afterwardThird-party API keys pasted in through a settings panel
Plaintext configReadable by the frontend, by designGenuinely non-secret configuration (a model name, a feature flag)

A consequence worth naming explicitly: verifying that a stored credential actually works can never be done by reading it back out for inspection — that path is intentionally blocked. Verification instead happens server-side, by making a real request with the stored credential and returning only the outcome (success or failure, an HTTP status) — never the credential itself.

Access control at the data layer is enforced by the backend platform's row-level security, scoped to a single authenticated owner account — this is intentionally a single-tenant system, not a multi-user product; anything resembling external client or affiliate "logins" elsewhere in the system are internal views for the owner, not real separate accounts.

Applied Surfaces

The architecture above supports a set of concrete, everyday surfaces built on top of it:

🏠

Home

Daily/weekly auto-generated reports, a daily meeting brief, at-a-glance operational stats.

🗂️

Operations

Collapsible, independently editable dashboards — CRM, ads, content, tasks, and more — each backed by the generic sheet engine.

🚪

Portals

Role-specific internal views (affiliate / client / ads) over the same underlying data, with computed summary stats.

📁

Repository

A private document store — files, spreadsheets, video, images, PDFs — with categorized browsing and search.

🗓️

Meetings Log

A persisted, deduplicated record of every generated daily brief and report, so nothing is regenerated (or re-billed) twice in a day.

📨

Conversations

Full transcript history across every connected messaging platform, browsable by contact.

Design Reflection

A few decisions in this system were deliberate trade-offs rather than obvious defaults, and are probably the most interesting parts to interrogate:

Provider-agnostic action grammar over native function calling

Native tool-calling APIs are more structured and better-supported, but tying the system to one provider's implementation would have broken the free-tier fallback cascade — many free-hosted models don't reliably support it. A plain-text convention parsed by the application itself is less elegant, but it's what makes "never hard-fail on availability" actually true.

A generic sheet engine instead of purpose-built schemas

Building a dedicated CRM table, a dedicated ads table, and so on would have been more "correct" relationally, but would also mean every new tracked category is a schema migration and new UI code. The generic sheet/column/row model trades some data-integrity guarantees (weaker typing, no foreign-key relationships between sheets) for the ability to add an entirely new tracked category as pure data, in seconds, with zero new code.

Single-tenant by design

The system deliberately does not attempt multi-user access control, real external client accounts, or tenant isolation — those are a substantially larger and different engineering problem (real authentication for other humans, permission boundaries, data isolation guarantees) that this system does not currently solve, and "portal" surfaces are explicitly internal views rather than a claim otherwise.

Defense-in-depth over trusting the model

Context scoping and the credential-verification pattern both reflect the same underlying stance: treat the model's output as untrusted input, not as a privileged instruction. The enforcement lives in the deterministic code path, not in prompt wording — the prompt shapes behavior, but the code is what actually decides what's allowed to happen.
